# uwnorm — 水中動画の露出・ホワイトバランス時間正規化

MP4 の水中映像から **AE ハンチングによる明滅** と **青緑カブリ** を取り除き、
時間方向に安定した明るさ・色にするツール。解析パスと適用パスの 2 パス構成で、
Docker コマンド 1 本で再現可能に実行できる。

要件定義書: [`underwater_video_normalizer_requirements_1.md`](underwater_video_normalizer_requirements_1.md)

```bash
make build
make run IN=dive.mp4 OUT=dive_norm.mp4 PRESET=deep_blue
```

## 1. 何をするツールか

MP4 は現像・ガンマ符号化・非可逆圧縮が済んでいるので、**フレーム単位の ISO 値は
復元できない**（要件 P-1）。本ツールがやるのは ISO を揃えることではなく、
**見かけの明るさと色を画素から測って時間方向に正規化する**こと。

| やること | やらないこと |
|---|---|
| AE ハンチング由来の明滅・ドリフト除去 | 白飛び・黒潰れの復元（P-2、情報が無い） |
| 水中の青緑カブリ補正と時間安定化 | 深度推定を用いた距離依存の色復元（Sea-thru 系） |
| シーンカットをまたがない区間処理 | バックスキャッター除去、ディヘイズ |
| 音声・データ・PTS の保持 | 手ブレ補正、レンズ歪み補正、HDR 入力 |

**意図的なシーン変化は残す。** 水面を向く、ライトを点ける、深場に降りる —— これらは
被写体の情報であって除去対象ではない。除去するのは「カメラが勝手に動いた分」だけ。
この切り分けが本ツールの設計の中心にある。

## 3. パイプライン全体像

```
                          ┌──────────── Pass 1: 解析 ────────────┐
MP4 ──► 低解像度デコード ──► 線形化 ──► ROI/マスク ──► ロバスト統計
        (長辺 384px)        (EOTF)                   ├─ 代表輝度 log L_t
                                                     ├─ フレーム間比 log r_t
                                                     ├─ チャネル別比 Δu_t
                                                     ├─ 照明色推定 u_t
                                                     └─ シーン記述子
                                                            │
                    ┌───────────────────────────────────────┘
                    ▼
             カット検出 ──► 区間分割
                    │
                    ├─► 露出: 累積 → アンカリング → 低/高周波分離 → クランプ
                    └─► WB  : 累積 → アンカリング → モード別適用 → クランプ
                                        │
                                        ▼
                                 analysis.json
                                （フレーム別ゲイン曲線）
                                        │
                          ┌─────────────┴──── Pass 2: 適用 ────┐
MP4 ──► フル解像度デコード ──► チャネル別ゲイン + ソフトクリップ ──► OETF
                                        │                          │
                                        ▼                          ▼
                                 （LUT に畳んで実行）         エンコード
                                                                   │
                       音声 / データ / メタデータ / PTS ──► 多重化 ──► 出力
```

2 パスにする理由は単純で、**全編の統計を見ないと「どこが flicker でどこが本当の
変化か」が決められない**から。1 パスの因果フィルタでは必ず補正が遅れ、明滅を
増やしてしまう。

## 4. アルゴリズム詳細

### 4.1 線形化（なぜ必須か）

測定もゲイン適用も、必ず**線形光**で行う（要件 F-02）。
`uwnorm/core/color.py`

MP4 に入っているのはガンマ符号化された非線形信号。これを直接 2 倍しても
「明るさが 2 倍」にはならず、コントラストまで変わる。フレーム間比
`I_t / I_{t-1}` も、非線形領域では露出比と一致しない。

```
符号化値 ──EOTF──► 線形光 ──測定/ゲイン──► 線形光 ──OETF──► 符号化値
```

対応 TRC は `srgb`（既定）/ `bt709` / `gamma22` / `gamma24` / `linear`。
コンテナに `color_transfer` があればそれを尊重し、無ければ `--input-trc` に従う。
民生アクションカメラの 8bit BT.709 ファイルは実質 sRGB なので既定は `srgb`。

### 4.2 ロバスト統計

`uwnorm/core/stats.py`

単純な `mean()` はこの用途では常に間違った推定量になる。理由と対策:

| 問題 | 単純平均だとどうなるか | 対策 |
|---|---|---|
| 白飛び画素 | 255 に張り付いた画素は真値を持たない。ゲインを上げても動かないので、平均が「露出は変わっていない」と誤報告する | **妥当画素マスク**: 符号化領域で `0.01 ≦ 値 ≦ 0.98` の画素のみ採用（クリップは符号化領域でしか定義できない） |
| 黒潰れ画素 | ほぼノイズ。比を取ると発散する | 同上（下限側） |
| 魚が横切る | 画面の 40% が別物になり、平均が大きく動く | **中央値ベースの比推定**（後述） |
| 露出は乗算的 | 算術平均はヒストグラム形状に依存する | **トリム済み幾何平均**: 0.5〜99.5 パーセンタイル内で `exp(mean(log I))`。露出が 2 倍なら必ず 2 倍になる |

**フレーム間比 `r_t` の推定**が、このツールで一番効いている部分:

```
r_t = median( I_t / I_{t-1} )   ただし両フレームで妥当な画素のみ
```

露出が動くと**全画素が同じ倍率**でスケールするので、画素ごとの比の中央値が
その倍率そのものになる。魚が横切っても変化するのは少数派の画素なので、
中央値は無視する。実測（テスト `test_ratio_estimate_ignores_a_moving_subject`）:
画面の 44% を占める遮蔽物があっても、1.3 倍の露出変化を誤差 2% 以内で回収する。

### 4.3 露出の時間正規化

`uwnorm/core/exposure.py`（要件 F-03）

測定値は 2 つあり、**それぞれ別の壊れ方をする**:

| 系列 | 内容 | 強み | 弱み |
|---|---|---|---|
| `L_t` | フレームのロバスト対数輝度 | 絶対値。ドリフトしない | シーン内容に汚染される（暗い壁に寄れば下がる） |
| `D_t` | `cumsum(log r_t)` | シーン内容に不感 | ノイズ増分の積分なので、数千フレームで徐々にズレる |

そこで**相補フィルタ**で良いとこ取りをする:

```
E_t = D_t − lowpass( D_t − L_t )
```

`D − L` は定義上ゆっくりしか変化しないので、この式は
「D の高周波（正確）」＋「L の低周波（ドリフトしない）」を合成することになる。
結果 `E_t` は、クリップ全体で比較可能な絶対スケールのドリフトフリー露出曲線。

*実測*: ノイズ増分を積分しただけの `D` は最大誤差 0.066、アンカリング後は 0.034
（テスト `test_anchor_beats_the_raw_integrator` が回帰を検出する）。

**補正モード**:

| `--exposure-mode` | 適用ゲイン | 出力される露出 |
|---|---|---|
| `deflicker`（既定） | `lowpass_τ(E) − E` | 低周波は保持、高周波だけ除去 = ダイブ本来の明るさ変化は残る |
| `lock` | `median(E) − E` | 全編を単一の目標露出に固定 |
| `off` | `0` | 何もしない |

ゲインは `--max-exposure-gain`（既定 ±1.5 EV）でクランプし、
クランプが発生したフレームは `analysis.json` に記録され警告が出る（N-06）。

### 4.4 ホワイトバランス

`uwnorm/core/wb.py`（要件 F-04, F-05）

#### 照明色の推定

線形光で照明の RGB を推定し、**G = 1.0 に正規化**して R/G・B/G の 2 自由度にする。
緑は水の吸収が最も少なく、4:2:0 でも最も密にサンプルされるチャネルなので、
ここを基準にすると露出の判断（4.3）と色の判断が独立に保てる。

| `--wb-method` | 中身 | 使いどころ |
|---|---|---|
| `shades-of-gray`（既定） | Minkowski 平均 `(mean(I^p))^(1/p)`、`p=5` | 水中の既定。`p=1` は水柱そのものに引っ張られ、`p→∞` は光のギラつき 1 点に張り付く。その中間 |
| `max-rgb` | 上位 1% 画素の平均 | 白い砂地やダイブスレートが写っている場合 |
| `gray-world` | `p=1` | 比較用ベースライン |
| `reference-frame` | 指定時刻・指定 ROI（グレーカード）を白基準にする | 撮影時にグレーカードを写してある場合。最も精度が高い |

#### 時間安定化 —— 平滑化だけでは色の明滅は消えない

ここは要件定義書の素直な読み（「推定ゲイン系列を平滑化して適用する」）から
**意図的に踏み込んでいる**部分なので、理由を書く。

フレームごとの推定値 `u_t` が揺れる原因は 2 つある:

1. **推定誤差** — 赤い魚が入ってきてフレームの平均色が変わった。照明は変わっていない。
2. **カメラの AWB ハンチング** — 記録された色が実際に変わった。

平滑化した推定値を適用すると、(1) は正しく抑えられるが、**(2) はそのまま残る**。
適用ゲインが滑らかでも、素材の色が毎フレーム動いているのだから出力も動く。
実際に最初の実装では、AWB ハンチングを入れた検証クリップで
WB 高周波変動の削減率が **−0.2% / −6.6%**（つまり悪化）だった。

解決策は露出と同じ構造 —— **チャネル別のフレーム間比**を使う:

```
ρ_c = median( I_c,t / I_c,t−1 )        （c = R, G, B、両フレームで妥当な画素のみ）
Δu_t = log ρ_R − log ρ_G               （R/G バランスの実変化）
U_t  = cumsum(Δu) − lowpass( cumsum(Δu) − smooth(u) )
C_t  = −U_t                            （中和に必要な対数ゲイン）
```

AWB が赤を上げれば**全赤画素が同じ倍率**で動くので中央値が捉える。
赤い魚が入ってきても少数派なので中央値は無視する。露出の `r_t` とまったく同じ論法。
これで `C_t` が高周波でも低周波でも信頼できる曲線になり、初めて色の明滅を
「除去」できる。修正後の実測は **100% / 97%**（下記 §10）。

**モード**:

| `--wb-mode` | 適用ゲイン | 出力の見え方 |
|---|---|---|
| `drift`（既定） | `C_t`（全周波数を補正） | 浅場でも深場でも中性。P-5 が言う「浅場と深場が混在するクリップ」に対応 |
| `fixed` | `C_t − lowpass_τ(C_t) + median(C)` | 単一の白基準で撮ったのと同じ見え方（深くなれば青くなる）＋ AWB ハンチングだけ除去 |
| `off` | `1.0` | 何もしない |

ゲインは `--max-wb-gain`（既定 3.0）でクランプ。4:2:0 クロマに強い赤ゲインを
掛けると色滲みとノイズが増幅されるため（P-4）、上限は必須。
`--chroma 422` / `444` で中間クロマを上げる選択肢も用意してある。

### 4.5 シーンカット検出

`uwnorm/core/cuts.py`（要件 F-06）

カットをまたいで平滑化すると前のショットの色が次のショットに半ウィンドウ分
引きずられる（A-4）。逆に**カットの誤検出も高くつく**: 露出積分器がリセットされ、
平滑化がそこで切れてしまう。両方向の精度が要る。

素朴なヒストグラム差分は使えない。実測で **カットスコアと露出変化の相関が 0.95**
になり、0.5 EV の AE ステップが本物のカットと同じスコアを出した。
つまり、パイプラインが測ろうとしているもの自体を検出器が拾ってしまう。

本ツールの記述子は、**対角ゲイン（= まさに露出と WB）に対して不変**に作ってある:

1. **ゲイン不変ヒストグラム** — 各チャネルを*自身の平均で割って* log2 領域でビン化。
   任意のチャネル別ゲインは相殺され、シーンの変化だけが残る。
2. **ゲイン不変サムネイル** — 同じ正規化をした 16×16 の縮小画像。
   ヒストグラムは順序情報を捨てるので、「統計的に似た別シーン」を見分けられない。
   レイアウトを粗く保持することで補う。
3. **移動探索** — サムネイル比較は ±3 画素のシフトを試して最小値を取り、
   重なり領域のみ比較する（パンで新しく入ってきた領域を不一致に数えない）。

スコアは 2 つの大きい方。それぞれ逆方向に壊れる（ヒストグラムは配置に鈍感、
サムネイルは動きに敏感）ので、どちらかが反応すれば検出できる。

*実測*（合成クリップ 4 種、`--cut-threshold` は既定 0.35）:

| クリップ | 検出結果 | 最大スコア | 背景スコア |
|---|---|---|---|
| 静止・カット無し | なし ✅ | 0.035 | 0.032 |
| ハードカット @100 | `[100]` のみ ✅ | 0.443 | 0.034 |
| 高速パン（12px/frame）・カット無し | なし ✅ | 0.329 | 0.323 |
| 高速パン + カット @100 | `[100]` のみ ✅ | 0.548 | 0.321 |

移動探索を入れる前は、高速パンだけで **65 個の誤検出**が出ていた。
なお高速パンのマージンは薄い（0.329 vs 閾値 0.35）。これは 320px 幅で
毎フレーム 12px = 毎秒画面幅 1.1 個分という極端なホイップパンなので通常は問題ないが、
そういう素材では `--cut-threshold` を上げるか `--cuts` で手動指定するとよい。

手動指定: `--cuts 00:12.3,01:45.0`（自動検出と OR される）。

### 4.6 時間フィルタ

`uwnorm/core/smooth.py`

全フィルタが守る 3 原則:

1. **カットをまたがない** — 系列をカットで分割し、区間ごとに独立に処理。
2. **端は反射** — ゼロ詰めすると各区間の先頭・末尾がゲイン 1.0 に引っ張られ、
   目に見えるランプが出る。
3. **ゼロ位相** — 因果フィルタだと補正が明滅に対して遅れ、かえって悪化する。

低周波／高周波の分離は**ゼロ位相 Butterworth**（`filtfilt`、実効 4 次）。
最初は Gaussian を使っていたが、減衰が緩すぎて `τ=1.5s` 設定でも
周期 5 秒の本物の明るさ変化を 1/4 も削ってしまい、F-03.4 が保持せよと言っている
シーンダイナミクスをちょうど潰していた。Butterworth に替えて
**高周波削減 67% → 94%**、かつ低周波は保持されるようになった。

`τ` の定義: カットオフ周波数 `fc = 1/τ`。つまり「**周期 τ 秒より速い変動は
AE ハンチング、遅い変動はダイブそのもの**」という指定になる。

短い区間（filtfilt のパディングが取れない長さ）は Gaussian に、
さらに短ければ区間の中央値にフォールバックする。

WB 推定値そのものの平滑化には `--smoother` が使える:
`savgol`（既定、ランプを保持する）/ `median-gauss`（1 フレームだけの外れ値に強い）。

### 4.7 ゲイン合成・ソフトクリップ

`uwnorm/core/gains.py`

**画素には 1 回しか触らない。** 露出も WB も線形光での乗算なので、
1 つのチャネル別 3 成分ゲインに畳み込む:

```
gain_R = exp(露出対数ゲイン) × WBゲイン_R
gain_G = exp(露出対数ゲイン)
gain_B = exp(露出対数ゲイン) × WBゲイン_B
```

別々に適用すると 8bit 量子化器を 2 回通ることになる。P-2 が言うように
元から余裕が無いので、まとめる。

**ハイライトはソフトクリップ**（F-03.6）:

```
y = k + (1−k)·tanh( (x−k)/(1−k) )        x > k のとき（k = --soft-clip-knee、既定 0.8）
```

ニー点 `k` で値も傾き（= 1）も連続なので、そこに階調段差が出ない。
ハード `min(x, 1)` だと、ゲインが掛かったハイライトが平坦に潰れ、
さらに 3 チャネルが別々のゲインでクリップするため**色が転ぶ**（青被りなど）。
テスト `test_soft_clip_is_monotonic_continuous_and_bounded` が単調性・連続性・
上限 < 1.0 を保証している。

### 4.8 赤チャネル補償

`--red-compensation ALPHA`（既定 0 = OFF、Ancuti 方式）

赤は水が最初に吸収する波長で、数メートルより深いと**そもそも赤信号が残っていない**。
残っていないものを掛け算で持ち上げてもノイズが増えるだけなので、
赤が暗い画素に限って緑から借りてくる:

```
R' = R + α·(mean(G) − mean(R))·(1 − R)·G
```

`(1 − R)` の項で効果が赤の暗い画素に限定されるので、もともと赤い被写体は触らない。
線形光で、WB ゲインの**前**に適用する。使用する平均値は解析パスで測って時間平滑化した
ものなので、フレーム間でポンピングしない。

これは画素ごとに緑を参照する非線形処理なのでチャネル別 LUT に畳めない（§5）。
`--red-compensation > 0` のときだけ要素ごとの演算パスに切り替わる。

## 5. 高速化

### LUT による畳み込み —— 最大の効き目

適用パスの画素処理はこうなっている:

```
符号化値 → EOTF → ×ゲイン → ソフトクリップ → OETF → 量子化
```

ここで重要なのは、**各段がそのチャネル自身の値だけのスカラ関数**であること。
そして入力は 8bit ＝ **1 チャネルあたり取り得る値は 256 通りしかない**。

つまりフレームごとの処理全体が **チャネル別 256 エントリの LUT** に畳める。
1080p フレームで約 3,700 万回の超越関数演算が **768 回**になる。

近似ではなく**完全に同一**の結果になる（同じ関数・同じ dtype・同じ入力値で表を作るため）。
テスト `test_lut_matches_the_elementwise_reference` が要素ごと実装との
バイト一致を検証している。

LUT の適用には `cv2.LUT` を使う。素朴な `np.take(lut[c], frame[..., c])` は
ストライド 3 のビューを 3 回舐めることになり 4K で 8.6 fps しか出ないが、
`cv2.LUT` はインターリーブ配置をそのまま読めて **113 fps** 出る。

| 4K フレームの画素処理 | スループット |
|---|---|
| 要素ごと（numpy） | 1.9 fps |
| LUT + `np.take` | 8.6 fps |
| LUT + CUDA（転送込み） | 20.8 fps |
| **LUT + `cv2.LUT`（採用）** | **113 fps** |

**結果として、この経路では GPU より CPU の方が速い。**
LUT 参照そのものより PCIe 転送の方が高いため。素直な事実なので、
LUT が使える場合は `--device` の指定によらず CPU で実行する。
GPU は要素ごとパス（`--red-compensation` 使用時）で使われる。

副作用として **CPU と GPU の出力がビット一致する**ようになった。
要素ごとパスでは CUDA の float32 超越関数が numpy と 1 ULP 違い、
稀に丸め境界で別の 8bit 値になっていた。LUT は常に numpy で作るので、
この差が構造的に消える（N-01 にとって望ましい）。

### 3 段パイプライン

```
デコード(PyAV) → キュー → ゲイン適用 → キュー → エンコード(PyAV)
```

3 スレッドで動かす。libavcodec も OpenCV も処理の大半で GIL を解放するので、
実際に重なって動く。キューは上限付き（6 フレーム）なので、
**ピークメモリはクリップ長ではなくフレームサイズに比例する**（N-03）。

### その他

- 解析パスは長辺 384px にダウンスケールしてデコードする（swscale 内で縮小）。
  `--analysis-stride N` で N フレームに 1 回だけ測定でき、ゲインは線形補間される
  （ゲインは元々平滑なので補間誤差は出ない）。
- `--encoder x264_nvenc` / `x265_nvenc` で NVENC が使える（4K で 2.5 倍速）。
- `--hwaccel cuda`（NVDEC）は**実測で逆効果**だった: 32 fps 対 ソフトウェア 66 fps。
  LUT もエンコーダも RGB をホスト側で要求するため、デコードの節約分より
  ダウンロードのコストが上回る。オプションは N-05 のために残してあるが既定は `none`。

## 6. CLI リファレンス

```bash
uwnorm <subcommand> [options]
```

| サブコマンド | 内容 |
|---|---|
| `analyze` | 解析のみ → `analysis.json` ＋ レポート |
| `apply` | `analysis.json` を読んで適用のみ |
| `run` | analyze + apply（ディレクトリ指定でバッチ処理） |
| `report` | 既存 json からレポート再生成 |
| `verify` | 出力を解析し直して A-1 / A-2 / A-5 を実測（NG なら終了コード 2） |
| `presets` | 同梱プリセット一覧 |

### 主なオプション

```bash
uwnorm run input.mp4 -o output.mp4 \
  --exposure-mode deflicker --exposure-tau 1.5 --max-exposure-gain 1.5 \
  --wb-method shades-of-gray --wb-mode drift --wb-tau 3.0 --max-wb-gain 3.0 \
  --red-compensation 1.0 \
  --roi center:0.6 --exclude-mask mask.png \
  --cut-threshold 0.35 \
  --encoder x264 --crf 16 \
  --report out/report.html --jobs 8
```

| グループ | オプション |
|---|---|
| 解析 | `--input-trc` `--analysis-size` `--analysis-stride` |
| 露出 | `--exposure-mode {deflicker,lock,off}` `--exposure-tau` `--max-exposure-gain` |
| WB | `--wb-method {shades-of-gray,max-rgb,gray-world,reference-frame}` `--wb-p` `--wb-mode {drift,fixed,off}` `--wb-tau` `--max-wb-gain` `--red-compensation` `--reference-frame` `--reference-roi` `--smoother {savgol,median-gauss}` |
| カット | `--cut-threshold` `--cuts 00:12.3,01:45.0` |
| ROI | `--roi center:0.6` or `x,y,w,h` / `--exclude-mask PNG or x,y,w,h` / `--highlight-exclude` `--shadow-exclude` |
| 出力 | `--encoder {x264,x265,prores,ffv1,x264_nvenc,x265_nvenc}` `--crf` `--encoder-preset` `--chroma {420,422,444}` `--bit-depth {8,10}` `--profile archive` `--denoise {off,hqdn3d,nlmeans,vaguedenoiser}` `--soft-clip-knee` |
| 性能 | `-j/--jobs` `--device {auto,cpu,cuda}` `--hwaccel {none,cuda}` |
| 検証 | `--preview-range 00:30-00:45` `--compare` `--dry-run` `--verify` |
| 設定 | `--config <preset名 or YAML>` `--cache-dir` `--log-jsonl` `-v` |
| バッチ | 入力にディレクトリを渡す＋`--parallel N` |

**設定の優先順位**（F-09）: `dataclass 既定値` < `--config`（プリセット / YAML） < `明示したフラグ`。
全オプションの既定値が `None` なので、「指定しなかった」と「既定値を指定した」が
区別でき、この 3 層マージが成立する。

**ROI / 除外マスク**（F-07）: 統計の質は測る画素で決まる。
`--roi center:0.6` で中央のみ、`--exclude-mask` でドームポート反射やライトの
ホットスポットを除外できる（PNG の白 = 除外、または矩形指定）。

## 8. analysis.json とゲイン曲線の手修正

`analysis.json` はフレーム単位の統計・推定ゲイン・カット位置をすべて持つ（F-10）。
アーティストの介入点はここ:

```jsonc
{
  "frames": {
    "index": [...], "time": [...], "pts": [...],
    "log_luma": [...],            // 測定した対数輝度
    "log_ratio": [...],           // フレーム間比
    "exposure_curve": [...],      // アンカリング後の E_t
    "exposure_log_gain": [...],   // ← 手修正できる
    "wb_raw_r": [...],            // 素のフレーム毎推定
    "wb_curve_r": [...],          // アンカリング後の C_t
    "wb_gain_r": [...],           // ← 手修正できる
    "wb_gain_b": [...],           // ← 手修正できる
    "cut_score": [...], "valid_fraction": [...],
    "exposure_clamped": [...], "wb_clamped": [...]   // N-06
  },
  "metrics": { "exposure": { "reduction_pct": 96.2 }, ... }
}
```

```bash
uwnorm analyze dive.mp4 -a curves.json      # 曲線を出す
$EDITOR curves.json                          # 手で直す
uwnorm apply dive.mp4 -o out.mp4 -a curves.json   # 再解析せずに適用
```

`apply` は曲線を読むだけで再導出しない（`test_edited_gain_curve_is_used_verbatim`）。
`--cache-dir` を使うと解析済みのファイルは再利用されるので、
適用パスから再開できる（N-04）。

レポート（`--report out.html`）は自己完結 HTML（PNG を data URI 埋め込み）で、
露出曲線の Before/After、適用ゲインとクランプ、WB の素推定 vs 適用値、
カットスコアと閾値を出す。クリップがおかしいときに最初に見る場所。

## 11. 実測性能

測定環境: **AMD Ryzen 7 3700X（8 コア / 16 スレッド）**、RTX 3090、ffmpeg 4.4.2。
N-02 が想定する「16 コア CPU」の**半分の物理コア数**である点に注意。

| 素材 | パス | 設定 | 実時間比 |
|---|---|---|---|
| 1080p30 | 解析 | 既定 | 0.38× |
| 1080p30 | 適用 | x264 medium, CPU | **1.81×** |
| 1080p30 | 適用 | x264 medium, CUDA | 1.69× |
| 4K30 | 解析 | 既定 | 1.37× |
| 4K30 | 適用 | x264 medium | 5.56× |
| 4K30 | 適用 | x264 fast | 4.82× |
| 4K30 | 適用 | **h264_nvenc** | **2.12×** |
| 4K30 | 適用 | hevc_nvenc | 2.34× |

- **1080p は N-02 の「実時間の 2 倍以内」を CPU のみで達成**（1.81×）。
  LUT + `cv2.LUT` 導入前は 13.06× で、大幅に未達だった。
- **4K は NVENC 使用時に N-02 の「5 倍以内」を達成**（解析 1.37× + 適用 2.12× = 3.49×）。
  CPU のみ（x264 medium）では合計 6.93× で未達。ただし律速は x264 エンコード自体
  （エンコード単独で 4.4×）であり、N-02 が前提とする 16 物理コアなら達成見込み。
  実機では `--encoder-preset fast` または `--encoder x264_nvenc` を推奨する。
- ピーク RSS は 4K で 3.5 GB（N-03 の 8 GB 以内 ✅）。

## 12. 設計上の判断と、要件との差分

実装中に測って分かったことから、要件定義書の素直な読みから変えた点を明記する。

| 箇所 | 要件の記述 | 実装 | 理由 |
|---|---|---|---|
| WB 時間安定化 | 推定ゲイン系列に Savitzky-Golay 等を適用 | **フレーム間チャネル比の積分＋アンカリング**を追加し、その上でモード別に適用 | 平滑化した推定値を適用するだけでは、AWB ハンチング由来の色の明滅が**まったく減らない**（実測 −0.2% / −6.6%）。`--smoother` は絶対推定値の雑音除去として今も使っている |
| 低/高周波分離 | カットオフ時定数 | Gaussian → **ゼロ位相 Butterworth** | Gaussian は減衰が緩く、τ=1.5s でも周期 5 秒の本物の変化を 1/4 削っていた。削減率 67% → 94% |
| カット検出 | ヒストグラム差分／SSIM 等 | **ゲイン不変ヒストグラム + ゲイン不変サムネイル + 移動探索** | 素のヒストグラムは露出変化と相関 0.95 で誤検出。パン耐性のため移動探索も必要（誤検出 65 → 0） |
| 適用パス | 案 A: Python で float32 処理 | **チャネル別 LUT に畳んで実行** | 結果は完全に同一。1080p CPU が 13.06× → 1.81× 実時間比 |
| GPU | `--hwaccel` で NVDEC/NVENC | NVENC は有効、**NVDEC は既定 OFF**。LUT 経路は CPU 実行 | 実測で NVDEC は逆効果（32 fps 対 66 fps）。LUT 参照は PCIe 転送より速い |
| WB `fixed` の意味 | 区間全体のロバスト中央値に固定 | 適用ゲインの**低周波成分**を単一値に固定し、高周波は除去 | ゲインを文字通り定数にすると AWB ハンチングが出力に残る。「固定 WB で撮った映像」の見え方を再現しつつ明滅だけ消す |

**未決事項（要件 §12）への対応**: カメラ機種・グレーカードの有無・GPU 可否は
素材によって変わるので、すべてオプションとプリセットで切り替えられるようにしてある
（`--wb-method reference-frame`、`--device`、プリセット 4 種）。
「完全固定か明滅だけ消すか」は `--exposure-mode lock` / `deflicker` と
`--wb-mode drift` / `fixed` の組み合わせで選べる。

### v1 で実装していないもの

- 特徴点マッチによる動き補償（F-03.2 の v2 項目）。カット検出のサムネイル比較には
  簡易な移動探索が入っているが、露出比推定はグローバルのまま。
- 10bit 入力（出力は 10bit 対応済み）、HDR（PQ/HLG）入力。
- ディヘイズ／バックスキャッター除去。`--red-compensation` と同じ場所がフック点になる。
